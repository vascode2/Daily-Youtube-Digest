## [2022년식 방식의 청킹은 이제 그만 — Yuval Belfer, AI21 Labs](https://www.youtube.com/watch?v=r9OwPx_HoV0)

**한 줄 인사이트**
💡 단일 청크 크기에 의존하는 방식은 20~40%의 리콜 손실을 유발하므로, 모든 윈도우 크기로 인덱싱한 뒤 상호 순위 융합(RRF)으로 병합해야 합니다.

**핵심 요약**
AI21 Labs의 유발 벨퍼는 질의마다 필요한 청크 크기가 다르지만 인덱싱 시점에는 어떤 질문이 올지 알 수 없는 근본적인 딜레마를 지적합니다. 고정된 크기의 청킹이 가진 손실을 극복하기 위해 모든 규모로 데이터를 인덱싱하고 문서 단위로 순위를 통합하는 멀티스케일 인덱싱 전략을 제안합니다.

1. **청킹의 딜레마와 정보 손실**
   - 세인필드 대본 실험에서 보듯 구체적인 단어는 작은 청크가 유리하지만, 여러 문장에 걸친 맥락은 큰 청크가 필요해 단일 크기 청킹은 20~40%의 리콜 손실을 초래합니다.
   - 인덱싱 시점에는 윈도우 크기를 통제할 수 있지만 질문을 알 수 없고, 검색 시점에는 질문을 알지만 윈도우가 이미 고정되는 정보 불일치가 발생합니다.

2. **오라클 실험을 통한 비용 측정**
   - 연구팀은 여러 데이터셋을 6가지 다른 청크 크기로 복제한 뒤, 질의마다 가장 잘 작동하는 크기를 선택하는 오라클 실험을 진행했습니다.
   - 임의로 설정한 512 토큰 같은 단일 선택 방식이 그동안 성능 저하라는 보이지 않는 비용을 치르게 했다는 점을 확인했습니다.

3. **멀티스케일 인덱싱과 상호 순위 융합**
   - 이 문제를 해결하기 위해 코퍼스를 모든 윈도우 크기로 인덱싱하고 각각 질의를 수행한 뒤 전체 문서를 반환하여 순위를 비교 가능하게 만듭니다.
   - 크기가 다른 청크들의 결과를 상호 순위 융합(Reciprocal Rank Fusion)으로 병합하는 간단한 스크립트 방식을 사용합니다.

4. **성능과 비용의 실질적 평가**
   - 4개 데이터셋에 걸친 테스트 결과 모델 추가 없이 검색 성능을 높일 수 있으며, 실제 비용은 메모리가 2~5배 늘어나는 것 외에 지연 시간은 거의 추가되지 않습니다.

## [Where RL Will Take Search — Maximilian-David Rumpf, SID.ai](https://www.youtube.com/watch?v=iJVxxxHM_Oc)

**한 줄 인사이트**
💡 에이전트 검색에 강화학습을 적용하면 기존 프론티어 모델 대비 20배 빠르고 100배 저렴한 비용으로 최적의 문서를 찾아낼 수 있습니다.

**핵심 요약**
연사 Maximilian-David Rumpf는 AI 에이전트가 직면한 검색 비용의 한계를 분석하고, 전통적 파이프라인의 구조적 결함을 지적합니다. 컴퓨터 비전과 체스 AI가 거친 진화 과정을 검색 분야에도 적용하여 강화학습 기반의 최적화가 왜 필수적인지 설득력 있게 풀어냅니다.

1. **에이전트 검색의 비용과 기회**
   - 에이전트 토큰의 30%에서 50%가 검색에 소모되며, 이는 작업 수행 전에 대부분 집중됩니다.
   - 에이전트 방식은 검색 엔진보다 올바른 문서를 찾을 확률을 두 배 높이지만, 비용이 100~1000배 비싸고 수 분이 소요됩니다.

2. **클래식 파이프라인의 한계**
   - 기존 방식은 쿼리 재작성, 백엔드 호출, 리랭킹 단계의 모든 결정이 설계 시점에 고정되어 유연성이 떨어집니다.
   - 리랭커가 결과를 찾지 못했다는 것을 인지해도 이를 시정할 방법이 없어 부적절한 결과를 그대로 반환하게 됩니다.

3. **머신 디자인과 강화학습의 적합성**
   - 검색은 컴퓨터 비전과 체스가 거친 것처럼 수작업 룰 기반에서 스스로 학습하는 시스템으로 진화하고 있습니다.
   - 정답 여부가 명확히 검증 가능하고 매초 수천 번의 시도가 가능해 강화학습에 최적화된 환경을 제공합니다.

4. **성능 및 비용 혁신 결과**
   - 특화된 모델은 동일한 작업을 프론티어 모델 대비 5초 대 2분의 속도로 20배 빠르게 처리합니다.
   - 비용 또한 기존 방식의 약 100분의 1 수준으로 낮추며 효율성을 극대화합니다.

## [수십억 개의 법률 문서에 AI 연결하기 — Simon Eskildsen(turbopuffer) & Jacob Lauritzen(Legora)](https://www.youtube.com/watch?v=V-isu4eTHgw)

**한 줄 인사이트**
💡 법률 문서 검색 시스템에서 활성 프로젝트와 비활성 프로젝트를 동일 파티션에 섞어 저장하면 캐시 스래싱으로 검색 지연이 20초까지 폭증할 수 있으며, 프로젝트별 네임스페이스 격리와 객체 스토리지 활용이 이를 해결하는 핵심이다.

**핵심 요약**
Legora와 turbopuffer의 엔지니어들은 대규모 법률 문서 검색 시스템을 구축하고 운영하는 과정에서 겪은 아키텍처 시행착오와 해결책을 공유한다. Jacob Lauritzen은 단일 및 지역별 검색 클러스터의 한계와 데이터베이스 통합 과정에서 발생한 성능 저하 문제를 진단하고, 프로젝트 단위 네임스페이스 도입을 통해 비용과 성능을 최적화한 과정을 설명한다. 이어 Simon Eskildsen은 규제 산업 고객들이 요구하는 물리적 격리와 암호화 키 관리의 실질적 구현 방식, 그리고 스토리지 엔지니어링 관점에서의 최적화 기법을 해설한다.

1. **검색 지연 폭증과 캐시 스래싱 문제**
   - 법률 작업 특성상 집중적으로 쓰이다 버려지는 프로젝트들이 활성 프로젝트와 같은 파티션에 섞이면서 거대한 파티션이 메모리를 독점하고 캐시를 망가뜨렸다.
   - 이를 해결하기 위해 프로젝트를 저장소의 기본 단위로 삼고 각각을 독립된 네임스페이스로 분리하여, 사용되지 않는 프로젝트는 비용이 들지 않는 객체 스토리지에 머물도록 설계했다.

2. **규제 산업을 위한 네임스페이스 기반 격리**
   - 네임스페이스를 데이터의 최소 단위로 설정하면 은행이나 대기업이 요구하는 것처럼 각 고객마다 독립된 암호화 키와 버킷을 부여할 수 있다.
   - SSD 캐시 내부의 복잡한 암호화 구현 대신 캐시 자체를 아예 비활성화하는 실험을 진행했고, 성능 저하가 감수할 만한 수준임을 확인하여 이를 채택했다.

3. **스토리지 엔지니어링과 검색 최적화**
   - 객체 스토리지 환경에서는 왕복 지연 시간이 성능을 좌우하므로, 그래프 구조를 탐색하는 것보다 데이터를 트리 형태로 클러스터링하는 것이 훨씬 유리하다.
   - 100밀리초였던 P99 검색 지연이 20초까지 치솟았던 원인을 분석하고, 웹 스케일에서 벡터 검색과 전문 검색(full text search)의 비용 구조를 비교한다.
