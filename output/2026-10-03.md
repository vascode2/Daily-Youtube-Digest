## [What Makes Open Models Fast in Production — Sujee Maniyam, Nebius](https://www.youtube.com/watch?v=TRe1u7dHYiA)

**한 줄 인사이트**
💡 오픈 소스 LLM을 프로덕션 환경에서 빠르고 저렴하게 서빙하기 위해서는 하드웨어 최적화부터 캐시 인식 라우팅, 투기적 디코딩까지 인프라 전반의 정밀한 레이어별 최적화가 필수적입니다.

**핵심 요약**
Nebius의 Dylan Bristot과 Sujee Maniyam은 독점적 모델에 대적할 만큼 성장한 오픈 소스 LLM을 실제 서비스 환경에서 효율적으로 운영하기 위한 실전 전략을 제시합니다. 이들은 자체 호스팅과 상용 API 간의 비용 및 제어권 트레이드오프를 분석하고, 하드웨어 가속부터 추론 엔진 최적화에 이르는 기술적 해결책을 설명합니다. 궁극적으로 Nebius Token Factory를 통해 복잡한 인프라 관리 없이도 초고속 추론 성능을 달성하는 구체적인 아키텍처 최적화 방안을 공유합니다.

1. **오픈 소스 LLM 도입의 트레이드오프와 라이프사이클**
   - Nebius의 Dylan Bristot은 상용 API 사용 대비 자체 호스팅이 가져다주는 비용 절감 및 데이터 제어권의 이점과 함께, 추론, 데이터 수집, 사후 학습, 배포로 이어지는 전체 루프의 관리 필요성을 강조합니다.
2. **하드웨어 및 추론 엔진 레이어의 최적화**
   - Sujee Maniyam은 최신 NVIDIA 하드웨어에서 지원하는 NVFP4 포맷 활용법과 함께, 서비스 요구사항에 맞는 최적의 추론 엔진을 선택하는 것이 고성능 서빙의 첫걸음임을 설명합니다.
3. **캐시 인식 라우팅과 투기적 디코딩 기술**
   - KV 캐시를 재사용하는 캐시 인식 라우팅과 자체 트래픽 기반의 맞춤형 초안 모델을 활용한 투기적 디코딩을 통해 추론 지연 시간을 극적으로 단축할 수 있습니다.
4. **KV 캐시 오프로딩 및 프리필-디코드 분리**

## [GPU Died. Training Didn't: Self-Healing Training at Scale — Crusoe](https://www.youtube.com/watch?v=bRGyYaE0lxI)

**한 줄 인사이트**
💡 Crusoe는 Kubernetes 위에 Managed Slurm을 구축하여 GPU 하드웨어 장애 발생 시 사람의 개입 없이 15분 이내에 자동으로 훈련을 복구하는 자가 치유 인프라를 실현했습니다.

**핵심 요약**
Crusoe의 Connor Guerrero, Young Jeong, Nikhil Gupta는 대규모 GPU 클러스터에서 필연적으로 발생하는 하드웨어 장애를 해결하기 위해 Kubernetes와 Slurm을 결합한 새로운 아키텍처를 제시합니다. 이들은 기존 Slurm의 스케줄링 강점과 Kubernetes의 유연한 리소스 관리 및 관측 가능성을 통합하여 인프라 관리 부담을 최소화하는 방법을 설명합니다. 나아가 실제 GPU 장애 상황을 가정하고 사람의 개입 없이 15분 만에 체크포인트로부터 훈련을 자동 복구하는 'AutoClusters' 기술의 실전 데모를 통해 자가 치유 인프라의 강력한 성능을 입증합니다.

1. **기존 Slurm의 한계와 Kubernetes의 결합 이유**
   - Slurm은 연구자들에게 익숙한 sbatch 워크플로우와 토폴로지 인식 스케줄링을 제공하지만, 동적 리소스 할당과 노드 상태 감지 및 관측 가능성 측면에서 한계를 가집니다.
   - Crusoe는 두 개의 독립된 스택을 운영하는 대신, Kubernetes 위에 Managed Slurm을 구축하여 연구자와 플랫폼 팀 모두의 작업 방식을 바꾸지 않고도 관리 효율성을 극대화했습니다.

2. **자가 치유 기술 AutoClusters의 자동 복구 메커니즘**
   - AutoClusters는 XID 79와 같은 GPU 하드웨어 에러가 감지되면 자동으로 알림을 보내고, 문제가 발생한 노드를 드레인(Drain) 및 대체합니다.
   - 이후 사람의 개입 없이 자동으로 작업을 다시 큐에 대기시키고(Requeue), 기존 체크포인트에서부터 훈련을 재개(Resume)하는 전체 워크플로우를 수행합니다.

3. **실제 GPU 장애 상황에서의 15분 복구 데모**
   - 발표자들은 훈련 도중 인위적으로 GPU 장애를 발생시킨 뒤, 시스템이 이를 감지하고 새로운 노드로 대체하여 15분 이내에 훈련을 정상화하는 과정을 직접 시연합니다.
   - 이 자동화된 복구 프로세스는 새벽 시간대에 엔지니어가 수동으로 장애를 해결해야 하는 번거로움을 완전히 없애 대규모 클러스터 운영의 확장성을 보장합니다.

4. **학습과 추론 간의 유연한 GPU 자원 공유**
   - Kubernetes 기반의 단일 인프라 스택을 활용함으로써 수요 변화에 따라 학습(Training)과 추론(Inference) 워크로드 간에 GPU 자원을 동적으로 공유할 수 있습니다.
   - 이를 통해 유휴 자원을 최소화하고 하드웨어 활용도를 극대화하여 클라우드 비용을 효율적으로 절감할 수 있는 기반을 마련합니다.

## [An Interaction Is All You Need — Ivan Leo, Google DeepMind](https://www.youtube.com/watch?v=8aVbXXvJUY4)

**한 줄 인사이트**
💡 구글 딥마인드는 기존 API의 한계를 극복하고 에이전트 환경을 효율적으로 관리하기 위해 서버 사이드 상태 관리와 영구 샌드박스를 지원하는 Gemini Interactions API 및 Managed Agents를 출시했습니다.

**핵심 요약**
구글 딥마인드의 개발자 경험 엔지니어인 이반 레오(Ivan Leo)가 에이전트 워크로드에 최적화된 새로운 Gemini Interactions API와 Managed Agents를 소개합니다. 그는 기존의 단일 완료(completion) 방식 API가 에이전트의 복잡한 상태 관리와 도구 사용을 감당하지 못하는 문제를 지적하며, 서버 사이드 상태 유지와 강력한 멀티모달 출력을 지원하는 새로운 아키텍처를 제시합니다. 나아가 클라우드 기반의 영구적인 원격 샌드박스 환경에서 안전하게 에이전트를 실행하고 관리할 수 있는 구체적인 데모와 활용법을 공유합니다.

1. **에이전트 워크로드를 위한 새로운 API 패러다임의 필요성**
   - 기존의 단일 완료(completion) 기반 API는 에이전트가 추론하고 행동하는 과정에서 발생하는 복잡한 상태 변화와 생각의 흐름(thought signatures)을 개발자가 직접 관리해야 하는 한계가 있었습니다.
   - 구글 딥마인드는 이러한 수동 상태 관리의 번거로움을 해결하기 위해 상호작용 ID(interaction IDs)를 통해 서버 사이드에서 상태를 유지하는 Interactions API를 설계했습니다.

2. **서버 사이드 상태 관리와 강력한 멀티모달 체이닝**
   - 새로운 API는 동일한 컨텍스트 내에서 이미지, 비디오, 오디오 생성을 자연스럽게 연결할 수 있도록 지원하며, 개발자가 생각의 흐름을 직접 파싱할 필요 없이 서버가 이를 안전하게 처리합니다.
   - 또한, 엄격한 타입 지정을 통한 멀티모달 출력(strongly typed outputs)과 내장 도구 및 사용자 정의 도구의 유연한 결합을 지원하는 새로운 단계(steps) 데이터 모델을 제공합니다.

3. **Managed Agents를 통한 클라우드 기반 영구 샌드박스 환경**
   - Managed Agents는 원격의 안전한 샌드박스 환경에서 Antigravity 하네스를 실행하며, 환경 ID(environment IDs)를 통해 상태를 지속적으로 유지합니다.
   - 구글 클라우드 스토리지(GCS), GitHub, 인라인 파일 등 다양한 소스로부터 코드를 직접 로드할 수 있어, 최대 200만 토큰에 달하는 대규모 리포지토리를 분석하는 작업을 효율적으로 수행합니다.

4. **보안 자격 증명 프록시와 오픈소스 Gemini API CLI 지원**
   - 에이전트가 외부 도구를 안전하게 사용할 수 있도록 자격 증명을 주입하는 프록시(credential-injecting proxy) 기능을 제공하여 보안성을 크게 높였습니다.
   - 이와 함께 오픈소스로 제공되는 Gemini API CLI를 통해 로컬과 클라우드 환경 모두에서 동일한 에이전트를 손쉽게 배포하고 테스트할 수 있도록 지원합니다.

**한 줄 인사이트**
💡 단순한 샌드박스를 넘어선 완전한 개발 환경과 의존성을 갖춘 데브박스(Devbox)가 AI 에이전트 구동에 필수적인 요소로 대두되고 있습니다.

**핵심 요약**
최근 AI 개발 환경의 변화 속에서 단순 격리 환경의 한계를 지적하며 완전한 개발 시스템의 필요성을 조명합니다. 다양한 공식 소스와 업계 업데이트를 바탕으로 에이전트 운영 시 마주하는 구조적 한계와 해결 방향을 짚어냅니다.

1. **샌드박스 환경의 한계**
   - 기존의 단순 샌드박스 방식만으로는 실제 개발 환경에서 요구되는 복잡한 의존성을 온전히 충족하기 어렵습니다.
   - AI 에이전트가 원활하게 코드를 작성하고 테스트하기 위해서는 모든 패키지와 설정이 포함된 종합적인 환경이 필수적입니다.

2. **데브박스의 필요성**
   - 에이전트에게는 격리된 공간을 넘어 전체 개발 라이프사이클을 지원하는 데브박스(Devbox)가 요구됩니다.
   - 이를 통해 에이전트는 실제 개발자와 유사한 수준의 도구 접근성과 실행 환경을 확보하게 됩니다.

3. **향후 개발 생태계 전망**
   - OpenAI의 데브데이 등 최신 기술 동향과 맞물려 에이전트 인프라 환경은 더욱 고도화될 것으로 보입니다.
   - 관련 하드웨어 가속 및 인프라 솔루션의 발전이 향후 AI 에이전트의 성능과 안정성을 좌우할 핵심 요인이 될 것입니다.
