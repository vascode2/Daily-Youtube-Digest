## [Guide, Verify, Solve — Anirban Chatterjee, Sonar](https://www.youtube.com/watch?v=03l29gJXpCE)

**한 줄 인사이트**
💡 AI가 작성한 코드의 생산성 향상은 일시적이며 '검증 부채'를 남기기 때문에, 인간의 맹목적인 수용을 방지하고 코드 품질을 유지하려면 제로 트러스트 기반의 다층적 자동 검증 루프를 도입해야 합니다.

**핵심 요약**
Sonar의 Anirban Chatterjee는 AI 도구로 작성된 코드가 장기적으로 '검증 부채'와 복잡성을 가중시키며, 인간 개발자의 검토만으로는 이를 걸러내기 어렵다고 지적합니다. 그는 AI 모델의 맹점을 보완하기 위해 코드 생성 전후를 모두 감싸는 제로 트러스트 기반의 다층적 검증 루프를 구축해야 한다고 주장합니다. 이를 통해 개발자가 직접 문제를 해결하는 대신 에이전트가 스스로 코드를 수정하고 품질 표준을 준수하도록 만드는 구체적인 방안을 제시합니다.

1. **AI 코드 생성의 한계와 검증 부채**
   - 카네기 멜런 대학의 연구에 따르면 AI 도구를 도입한 GitHub 프로젝트의 생산성 향상은 약 3달 뒤 정체되는 반면, 정적 분석 경고와 코드 복잡성은 그대로 남아 '검증 부채'로 축적됩니다.
   - 이러한 검증 부채의 해결 비용은 시스템의 중요도에 따라 급증하며, 외부 공격에 노출된 대규모 코드베이스일수록 AI 생성 코드와 실제 요구 품질 간의 격차가 치명적인 위협이 됩니다.

2. **인간 검토의 한계와 신뢰성 문제**
   - 와튼 스쿨의 연구 결과에 따르면, 참가자들은 AI의 조언이 맞을 때 92.7% 수용했을 뿐만 아니라, AI가 확신을 가지고 거짓말을 하도록 설정되었을 때도 약 80%의 확률로 그 제안을 그대로 따랐습니다.
   - 이는 AI가 제안한 코드를 인간이 맹목적으로 승인하는 '고무도장(rubber stamping)' 현상을 보여주며, 인간의 검토가 더 이상 확실한 방어선이 될 수 없음을 시사합니다.

3. **제로 트러스트 및 다층적 검증의 필요성**
   - AI가 생성한 코드는 출처를 불문하고 검증해야 하며, 모델 스스로 자신의 출력을 평가할 때 발생하는 편향을 피하기 위해 코드 생성 모델과 다른 방식으로 검증하는 제로 트러스트 원칙이 필요합니다.
   - 구문, 데이터 흐름, 아키텍처 등을 동시에 잡아내기 위해 연산 기반 검토(computational review)와 추론 기반 검토(reasoning-based review)를 병행하는 다층적 검증 체계를 갖춰야 합니다.

4. **Sonar의 벤치마크 결과와 에이전트 루프 설계**
   - Sonar의 리더보드 분석에 따르면 Claude 모델 중 하나는 정확성과 신뢰성에서 우수한 반면, 다른 모델은 유지보수성, 보안성, 낮은 복잡성 측면에서 더 나은 성능을 보여 모델마다 맹점이 다름을 입증했습니다.
   - 따라서 코드 생성 전 아키텍처 제약 조건을 에이전트에 전달하고, 내부 루프에서 즉각적인 검증과 자동 수정을 수행하여 오류가 다음 단계로 전파되는 것을 원천 차단해야 합니다.

## [Velocity Sickness: What Happens When Your Whole Team Gets 10x Faster — Matt Dailey, Ref.](https://www.youtube.com/watch?v=Kz4QJmNrVXU)

**한 줄 인사이트**
💡 AI 에이전트로 인해 개발 속도가 빨라지더라도 의사결정 레이어를 구현 레이어와 분리하지 않으면, 코드와 제품에 대한 통제력을 잃고 생산성 저하를 겪는 '속도 병(Velocity Sickness)'에 걸리게 됩니다.

**핵심 요약**
Ref의 Matt Dailey는 AI 에이전트 도입으로 생산성이 급증하면서 발생하는 부작용인 '속도 병(Velocity Sickness)'의 위험성을 경고합니다. 그는 에이전트가 중요한 의사결정을 내리게 방치할 때 엔지니어가 코드와 제품의 소유권을 상실하는 문제를 지적하며, 이를 해결하기 위한 구조적 접근법을 제시합니다. 특히 채팅 창 대신 지속 가능한 '문서(Document)'를 중심에 두고 의사결정과 구현 단계를 명확히 분리할 것을 제안합니다.

1. **속도 병(Velocity Sickness)의 정의와 부작용**
   - AI 에이전트로 인해 결과물은 폭발적으로 늘어나지만 실제 임팩트로 이어지지 못해 팀이 극심한 스트레스를 받는 현상을 의미합니다.
   - 개발 팀에서는 너무 많은 풀 리퀘스트(PR)가 쏟아지고, 다음 날 아침 코드를 전혀 알아보지 못해 결국 에이전트 파산을 선언하고 작업을 폐기하는 악순환이 발생합니다.
2. **의사결정 주도권 상실의 위험성**
   - 에이전트가 핵심적인 의사결정까지 내리게 되면 엔지니어는 더 이상 코드를 소유하지 못하고, 팀 전체가 제품에 대한 지배력을 잃게 됩니다.
3. **채팅 대신 문서 중심의 아키텍처 구축**
   - 일시적이고 고립된 채팅 기반 인터페이스 대신, 상태를 보존할 수 있는 지속 가능한 공유 문서(Durable Shared Doc)를 의사결정의 기본 단위로 삼아야 합니다.
   - 문서를 통해 컨텍스트를 유지하면 에이전트를 상태 비저장(Stateless) 방식으로 운영할 수 있어, 시스템 이해도를 높이고 동일한 맥락에서 여러 작업을 시작할 수 있습니다.
4. **실천 가능한 세 가지 즉각적 조치**
   - 현재 작업의 속도 단계를 인지하고, 계획(Plan)을 단순한 프롬프트가 아닌 시스템으로 들어가는 포털로 취급해야 합니다.
   - 에이전트에게 계획을 전달하기 전에 먼저 팀원에게 공유하여 검토를 거치는 협업 프로세스를 정착시켜야 합니다.
