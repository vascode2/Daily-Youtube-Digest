## [Weight Folding, CUDA Streams, and the Bug That Made My Model Speak Backwards — Filip Makraduli](https://www.youtube.com/watch?v=c1hGBoWw20A)

**한 줄 인사이트**
💡 RMS Norm의 연산을 가중치에 병합하고 CUDA 스트림을 병렬화하는 FlashNorm 기법을 통해, 모델 성능 저하 없이 노름 및 프로젝션 연산 속도를 33~35% 향상시킬 수 있습니다.

**핵심 요약**
AI 엔지니어 Filip Makraduli가 Nils Graef와 공동 연구한 FlashNorm 논문의 핵심 아이디어와 구현 과정에서 겪은 CUDA 스트림 버그 해결 과정을 공유합니다. 저자는 GPU가 연산보다 데이터 이동과 대기 시간에 더 많은 시간을 소비한다는 점에 착안하여, RMS Norm 레이어의 오버헤드를 줄이는 대수학적 최적화 기법을 제시합니다. 이를 통해 실제 모델 배포 환경에서 커널 레벨의 성능 최적화를 달성하는 구체적인 방법론을 설명합니다.

1. **FlashNorm의 핵심 대수학적 최적화 기법**
   - 오프라인 상태에서 노름의 게인(gain) 값을 프로젝션 가중치에 미리 병합(Weight Folding)하여 하나의 행렬이 두 연산을 모두 흡수하도록 만듭니다.
   - 스칼라 나누기 연산을 뒤로 미루고 연속된 이중 정규화 중 하나를 제거함으로써, 노름과 프로젝션 연산 속도를 33%에서 35%까지 향상시킵니다.
2. **CUDA 스트림을 활용한 병렬 하드웨어 가속**
   - 파이썬 레벨에서는 불가능한 최적화를 위해 CUDA 커널을 직접 작성하여 Tensor 코어에서는 행렬 곱셈을, CUDA 코어에서는 RMS 리덕션을 동시에 병렬로 실행합니다.
   - 이 기법은 torch.compile 및 양자화된 모델들과도 호환되어 기존 오픈소스 모델에 즉시 적용할 수 있는 실용성을 제공합니다.
3. **병렬 처리 중 발생한 1단계 지연 버그와 원인**
   - 테스트와 퍼플렉시티 측정은 통과했으나, 긴 문장 생성 시 이전 단계의 출력이 반복되는 1단계 지연(one-step lag) 현상이 발생했습니다.
   - 이는 두 CUDA 스트림 간의 결합이 암시적으로 처리되어, 행렬 곱셈이 끝나지 않은 상태에서 사후 스케일링 연산이 오래된 버퍼를 읽었기 때문입니다.
4. **명시적 동기화 해결책 및 Superlinked 엔진을 통한 배포**
   - 각 CUDA 스트림의 끝을 명시적으로 표시하고, 사후 스케일링 연산이 두 스트림의 완료를 모두 대기하도록 강제하여 레이스 컨디션 버그를 해결했습니다.
   - 임대형 엔드포인트에서는 커널 수정이 불가능하므로, 수정된 체크포인트를 배포하기 위해 Superlinked의 오픈 추론 엔진을 활용해야 합니다.

## [Two Bugs That Hid in Plain Sight: A vLLM Debugging Detective Story — Asaf Gardin & Yuval Belfer](https://www.youtube.com/watch?v=btxG75rNJC4)

**한 줄 인사이트**
💡 상태 저장형(Stateful) 추론 엔진인 vLLM에서 발생하는 간헐적인 오류는 단순한 쿼리 테스트로는 잡기 어려우며, GPU 메모리를 제한하고 로그 확률(logprob)을 추적하는 정밀한 디버깅을 통해서만 해결할 수 있습니다.

**핵심 요약**
AI21의 Asaf Gardin과 Yuval Belfer는 vLLM 환경에서 Jamba 모델을 구동할 때 1,000번 중 1번 꼴로 발생하는 기괴한 출력 오류의 원인을 추적합니다. 이들은 GPU 메모리 사용량을 인위적으로 낮추어 오류를 강제 재현하고, 로그 확률 비교와 요청 ID 추적을 통해 스케줄러와 메모리 캐시의 치명적인 버그들을 찾아냅니다. 상태 저장형 아키텍처의 복잡한 추론 과정에서 발생하는 무음 오류(Silent failure)를 어떻게 체계적으로 진단하고 해결했는지 그 과정을 상세히 공유합니다.

1. **GPU 메모리 제한을 통한 간헐적 오류의 강제 재현**
   - vLLM에서 Jamba 모델 실행 시 1,000번 중 1번 발생하는 무작위 오작동을 해결하기 위해, GPU 메모리 사용량을 90%에서 20%로 제한하여 8,854번째 요청에서 오류가 100% 재현되도록 유도했습니다.
   - 이를 통해 무작위로 보이던 버그가 메모리 압박과 특정 요청 스케줄링 하에서 반드시 발생하는 결정론적 문제임을 확인했습니다.

2. **요청 ID 추적을 통한 스케줄러의 디코드 순서 오류 발견**
   - 순방향 패스 내부 추적을 위해 요청 ID를 컨텍스트에 심고 분석한 결과, 스케줄러가 프리필(Prefill) 전에 디코드(Decode)를 먼저 실행하는 현상을 발견했습니다.
   - 어텐션 레이어와 달리 Mamba 레이어는 이전 상태를 먼저 읽기 때문에, 이 순서 오류로 인해 새로운 요청이 이전 요청의 잔류 데이터를 덮어써서 깨진 출력을 생성했습니다.

3. **32비트 인덱스 오버플로우로 인한 RL 학습 불안정성 해결**
   - 두 번째 버그는 강화학습(RL) 훈련 중 매 12단계마다 로그 확률이 급증하는 현상으로, 프롬프트당 롤아웃을 8개에서 128개로 늘리자 첫 단계부터 오류가 발생했습니다.
   - 원인은 40억 개를 초과하면서 랩어라운드(Wrap-around)되는 32비트 인덱스 변수였으며, 데이터 타입을 `size_t`로 변경하여 문제를 완전히 해결했습니다.

4. **상태 저장형 추론 엔진 디버깅의 교훈**
   - 두 버그 모두 Mamba 상태 캐시와 메모리 압박이라는 공통된 지점에서 발생했으며, 시스템이 크래시 없이 잘못된 답변을 높은 확신으로 출력하는 무음 오류의 위험성을 보여줍니다.

## [The Frontier AI Inference Cloud for Agents — Byung-Gon (Gon) Chun, FriendliAI](https://www.youtube.com/watch?v=Hvb2LfMH58c)

**한 줄 인사이트**
💡 에이전트 중심의 AI 추론은 기존 챗 방식과 달리 '작업(Task)' 단위로 작동하므로, 프리픽스 캐싱과 캐시 인식 라우팅을 통해 추론 효율을 극대화해야 합니다.

**핵심 요약**
연속 배칭(continuous batching) 기술을 개척한 FriendliAI의 전병곤 대표는 에이전트 AI 시대의 추론 패러다임 변화를 설명합니다. 그는 에이전트가 수행하는 반복적인 계획-실행-관찰 루프가 막대한 컨텍스트 중복을 유발한다고 지적하며, 이를 해결하기 위한 새로운 추론 아키텍처를 제안합니다. 오픈 가중치 모델과 FriendliAI의 최적화 스택을 결합하여 비용을 5.5배 절감하고 속도를 7배 향상시킨 실증 사례를 통해 에이전트 전용 클라우드의 필요성을 입증합니다.

1. **에이전트 추론과 기존 챗(Chat) 추론의 근본적인 차이**
   - 에이전트는 단발성 요청이 아니라 '계획-실행-관찰-반복'으로 이어지는 장시간의 '작업(Task)' 단위로 작동하며, 이 과정에서 컨텍스트가 계속 누적됩니다.
   - 매 호출마다 동일한 프리픽스(Prefix)를 반복해서 계산하는 것은 심각한 컴퓨팅 자원 낭비이며, 개별 호출의 지연 시간보다 전체 작업의 완료 시간이 핵심 지표가 됩니다.

2. **오픈 가중치 모델을 통한 비용 절감 효과**
   - 동일한 코딩 에이전트에게 타워 디펜스 게임 개발 작업을 수행하도록 한 실험에서, 오픈 가중치(Open Weight) 모델이 폐쇄형 프론티어 모델과 유사한 수준의 결과물을 냈습니다.
   - 이 과정에서 오픈 가중치 모델을 활용한 실행 비용은 폐쇄형 모델 대비 약 5.5배 저렴하여 에이전트 경제성을 크게 개선할 수 있음을 보여주었습니다.

3. **FriendliAI가 제안하는 에이전트 최적화의 4대 기둥**
   - 공유 프리픽스를 한 번만 계산하는 프리픽스 캐싱(Prefix Caching)과 GPU, 호스트 메모리, 디스크를 아우르는 계층형 KV 캐시 아키텍처를 구축했습니다.
   - 부하를 단순히 분산하는 대신 이미 프리픽스가 캐싱된 복제본(Replica)으로 요청을 보내는 캐시 인식 라우팅(Cache-aware routing)과 에이전트 인식 스케줄링을 적용했습니다.

4. **실제 고객 테스트를 통한 성능 및 비용 검증**
   - FriendliAI의 에이전트 전용 추론 스택을 적용한 고객사의 스플릿 테스트 결과, 에러율은 낮아지면서도 처리 속도가 기존 대비 7배 빨라졌습니다.
