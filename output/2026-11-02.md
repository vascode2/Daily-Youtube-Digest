## [AI Writes Code Faster Than Your Team Can Review It - Andrew Norrish, Sourcegraph](https://www.youtube.com/watch?v=-X3yXTwGs9A)

**핵심 요약**
Sourcegraph의 Andrew Norrish는 AI 기반 개발이 확산된 과정을 짚으며, 코드 생산 속도가 리뷰 역량을 앞지르면서 장애가 늘고 있다고 주장합니다. 그는 SRE를 더 채용하는 방식으로는 해결되지 않는다고 보고, 업계 데이터를 근거로 SRE와 플랫폼 팀의 역할이 더 중요해졌다고 설명합니다. 이어 코드 검색과 코드 그래프 기반 컨텍스트 엔진으로 대형 코드베이스의 문제를 조사·예방·복구하는 방법을 고객 사례로 보여줍니다.

1. **병목이 작성에서 리뷰로 이동**
   - AI 개발 도구가 보급되면서 코드 작성 속도는 크게 올라갔지만, 사람이 검토할 수 있는 양은 그대로입니다. 그 결과 코드 리뷰가 새로운 병목이 됩니다.

2. **SRE 증원만으로는 부족한 이유**
   - 코드 생산량이 빠르게 늘어나는 상황에서 SRE 인력을 늘리는 방식은 속도를 따라가지 못한다고 설명합니다.
   - 업계 데이터를 근거로 AI 코드가 장애 증가로 이어지는 흐름을 제시합니다.

3. **SRE·플랫폼 팀의 역할 확대**
   - AI 시대에는 SRE와 플랫폼 팀이 신뢰성의 기준을 세우고 대응 체계를 만들기에 가장 적합한 위치에 있다고 주장합니다.

4. **코드 검색과 코드 그래프로 조사·예방·복구**
   - Sourcegraph의 코드 검색과 코드 그래프 기반 컨텍스트 엔진은 방대한 코드베이스에서 장애 원인을 조사하고 예방과 수정까지 돕습니다.

## [Tiny Software Factories: Agentic Engineering DONE WRONG](https://www.youtube.com/watch?v=1v7ldJiyH-Y)

**한 줄 인사이트**
💡 에이전트 앞에서 매번 프롬프트를 치는 "인 루프" 대신 사람은 결과만 승인하는 "니어 루프"로 옮겨야 하며, 이를 위해 확장성은 포기하고 24시간 일하는 작은 소프트웨어 팩토리를 빠르게 만들라고 주장한다.

**핵심 요약**
IndyDevDan이 Phase 3 에이전틱 엔지니어링 강의의 맛보기로 "일부러 틀리게 하는" 방식을 소개한다. 그는 터미널에서 에이전트 하나와 주고받는 사람이 병목이고, 작업의 80% 이상은 적절한 시스템이 있으면 사람 없이 돌아간다고 말한다. 그래서 확장은 안 되지만 당장 쓸모 있는 지름길로 하나의 문제만 푸는 팩토리를 만든다는 흐름이다.

1. **병목은 사람, 해법은 니어 루프**
   - 인 루프에서는 사람이 프롬프트를 쓰고, 니어 루프에서는 에이전트가 이미 끝낸 일에 피드백하고 결정하고 승인한다.
   - 이 접근을 에이전틱 엔지니어링의 블리츠스케일링에 비유하며, 완벽함보다 출시를 우선하는 지역 최대치라고 설명한다.

2. **타이니 소프트웨어 팩토리의 정의**
   - 하나의 문제, 하나의 능동형 에이전트, 24시간 가동, 내구성 있는 환경, 그리고 루프 근처에 있는 사람이 핵심 조건이다.
   - 에이전트는 사람을 기다리지 않고 먼저 일한 뒤 대기하며, 샌드박스 안의 트리거가 이를 움직인다.

3. **일부러 택하는 안티패턴**
   - 에이전트 1개, 서버 내 cron, JSON 설정, 에이전트가 쓴 페이지, 단일 서버의 SQLite, 코드베이스 안의 bash를 지름길로 쓴다.
   - 각각 빠르게 가치를 내지만 어딘가에서 한계가 오며, 강의는 그 지점을 정확히 알게 해 준다고 한다.

4. **기능 지도와 에이전트 자기 수정**
