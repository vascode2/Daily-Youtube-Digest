## [AI 해커들은 당신의 모의 해킹보다 훨씬 빠릅니다 — Eli Cohen, Snyk](https://www.youtube.com/watch?v=f3o0-9Dlw3E)

**한 줄 인사이트**
💡 공격자들은 이미 프론티어 모델을 활용해 단 4분 만에 취약점을 연쇄 공격하므로, 연 1~2회 실시하는 전통적인 보안 점검 방식으로는 더 이상 대응할 수 없습니다.

**핵심 요약**
Snyk의 Eli Cohen은 개발자들이 전례 없는 양의 코드를 쏟아내는 에이전트 중심 시대에 기존 보안 모델이 어떻게 무너지고 있는지 분석합니다. 정적 분석(SAST)과 동적 테스트(DAST), 인간 기반 모의 해킹의 한계를 짚어본 뒤, 모든 코드 변경(PR)마다 AI 에이전트 팀을 투입해 실시간으로 공격을 시뮬레이션하는 지속적 공세 보안 전략을 대안으로 제시합니다.

1. **개발 속도와 AI 공격의 위협**
   - 개발자들이 생성형 AI를 이용해 대량의 코드를 배포하고 있으나 보안성이 담보되지 않은 경우가 많습니다.
   - 공격자 역시 프론티어 모델을 활용해 사소한 취약점들을 순식간에 치명적인 공격으로 체이닝하며, 가장 빠른 AI 공격은 불과 4분 만에 이루어집니다.

2. **전통적 보안 도구의 한계**
   - 정적 스캐닝(SAST)은 런타임 이슈를 잡지 못하고, 동적 테스트(DAST)는 복잡한 비즈니스 로직과 권한 부여 버그를 놓치기 쉽습니다.
   - 인간 모의 해킹은 비용이 높고 일 년에 한두 번에 불과해 급증하는 코드 배포 속도를 따라가지 못합니다.

3. **지속적 공세 보안과 에이전트 팀**
   - 모든 코드 변경(PR) 시점에 AI 에이전트가 직접 모의 해킹과 레드 테이밍을 수행하여 실시간으로 취약점을 검증해야 합니다.
   - 오케스트레이터, 정찰, 취약점 탐색, 익스플로잇 검증 판정관, 수정 및 리포팅 에이전트로 구성된 팀이 협업하여 오탐을 줄입니다.

## [소프트웨어 팩토리: 버그 리포트에서 프로덕션 코드까지 — Davis Palmie, Factory](https://www.youtube.com/watch?v=exiwa9QbQXI)

**한 줄 인사이트**
💡 소프트웨어 개발의 병목현상은 코딩 자체가 아니라 리뷰, 디버깅, 문서화, 테스트에 있으며, AI 에이전트 시대에는 토큰 리더보드가 아닌 신뢰할 수 있는 결과 중심 지표를 측정해야 한다.

**핵심 요약**
Factory의 데이비스 팔미(Davis Palmie)는 엔지니어의 역할이 직접 코드를 타이핑하는 것에서 에이전트를 관리하는 것으로 진화하고 있다고 설명합니다. 버그 리포트나 사용자 피드백 같은 입력 신호를 받아 프로덕션 코드까지 자동으로 전환하는 소프트웨어 팩토리의 개념을 제시하며, 비용 관리, 모델 선택, 조직 변화 등 리더들이 직면하는 핵심 질문에 답합니다. 나아가 모델 독립성, 소버린 배포, SDLC 통합 등 팩토리가 갖추어야 할 원칙과 성공적인 도입을 위한 8가지 에이전트 준비 요건을 상세히 짚어줍니다.

1. **소프트웨어 팩토리와 코딩 병목의 진실**
   - 엔지니어링의 본질적인 병목은 코드 작성 속도가 아니라 코드 리뷰, 디버깅, 문서화, 테스트 과정에 있음을 지적합니다.
   - Factory의 시스템은 버그 리포트나 사용자 피드백을 입력받아 에이전트 협업을 통해 자동으로 프로덕션 코드까지 완성하는 구조를 뜻합니다.

2. **소프트웨어 팩토리가 갖추어야 할 핵심 원칙**
   - 특정 AI 모델에 종속되지 않는 모델 독립성(model-agnostic)과 데이터 주권이 보장되는 소버린 배포(sovereign deployment)가 필수적입니다.
   - 개발 생명주기(SDLC) 전반에 걸쳐 통합되어야 하며, 모든 작업 표면에서 에이전트가 원활하게 작동할 수 있어야 합니다.

3. **에이전트 준비 상태를 위한 8가지 기둥**
   - 에이전트와 엔지니어 모두가 원활하게 협업할 수 있도록 시스템 전반의 성숙도를 높이는 8가지 아키텍처적 요건을 다룹니다.
   - 처음에는 전체 공정을 한 번에 바꾸기보다 인시던트 트리아지(incident triage)처럼 좁은 영역부터 시작해 점진적으로 범위를 넓혀야 합니다.

4. **토큰 리더보드를 넘어선 성과 지표**
   - 단순한 토큰 소비량 기반의 리더보드는 굿하트의 법칙(Goodhart's law)에 빠지기 쉬우므로 실제 성과 지표를 측정해야 합니다.
   - 신호에서 프로덕션까지 걸리는 시간(signal-to-production time), 인간의 개입 횟수, PR당 비용 등을 핵심 지표로 추적해야 합니다.

## [인공지능 에이전트들이 서로 대화할 수 없는 이유 (아직은)](https://www.youtube.com/watch?v=toq-jyGLZDk)

**한 줄 인사이트**
💡 인공지능 에이전트 간의 협업은 단순한 메신저나 프로토콜의 문제를 넘어, 정렬된 실시간 전송과 영속성을 요구하는 분산 시스템의 과제다.

**핵심 요약**
BAND의 공동 창립자이자 CTO인 Vlad Luzin은 단일 에이전트가 가진 주의 분산과 확증 편향의 한계를 지적하며, 앞으로의 인공지능은 에이전트끼리 직접 소통하는 방향으로 진화해야 한다고 주장한다. 그는 기존의 메신저 앱이나 MCP, A2A 프로토콜이 에이전트 간 협업을 온전히 지원하지 못하는 이유를 분석하고, BAND의 상호작용 레이어를 통해 이를 해결하는 방안을 제시한다.

1. **단일 에이전트의 한계와 수동 라우팅**
   - 개발자들이 Claude와 Codex를 나란히 실행하며 직접 결과물을 복사해 전달하는 라우터 역할을 하고 있으며, 루프 엔지니어링은 이를 스크립트로 대체하는 수준에 머물러 있다.
   - 컨텍스트 창이 아무리 커져도 단일 에이전트는 확증 편향과 주의 분산 문제에서 자유로울 수 없기 때문에 다중 에이전트 구조가 필수적이다.

2. **기존 도구와 프로토콜의 한계**
   - Slack이나 Telegram 같은 기존 메신저 앱은 에이전트 간의 자율적인 고속 통신을 처리하기에 구조적인 한계가 존재한다.
   - MCP와 A2A 같은 프로토콜 역시 에이전트 간 복잡한 상호작용과 협업을 완벽하게 소화하기에는 아직 부족함이 많다.

3. **분산 시스템으로서의 에이전트 연결**
   - 에이전트를 서로 연결하는 작업은 순서가 보장되는 실시간 전송, 데이터 영속성, 런타임 바인딩이 필요한 전형적인 분산 시스템 문제다.
   - 성공적인 에이전트 생태계를 위해서는 강력한 전송 계층 외에도 거버넌스, 식별성, 관측 가능성이 뒷받침되어야 한다.

4. **BAND 인터레이션 레이어와 실습 데모**
   - 밴드(BAND)는 에이전트들이 몇 초 만에 온보딩하고 서로 협업할 수 있는 전용 인터랙션 레이어를 새롭게 선보였다.
   - Claude Code와 Codex, LangGraph 에이전트들이 사용자 간에 경계를 넘어 서로 협력하는 실제 시연을 통해 글루 코드 없는 에이전트 연동의 가능성을 증명했다.
